# Nuvio hosted API and identity contract

Reviewed 2026-10-18 for [issue #3](https://github.com/saurabhhbansal/nuvioweb/issues/3). **Documentation only; no verifier, service permission exception, deployment or live account test is delivered.** [Plan and executed checks](plans/issues/issue-3.md). Human auth/security review is required before acceptance.

Owner decision, 2026-10-18: the project owner supplied the public documentation, accepted proceeding with documented public-client APIs without a separate permission letter, and authorized a public preview. Do not hold ordinary documented-client development for another permission request. The API reference hash was rechecked unchanged. Unlisted endpoint support, deployed session guarantees and separately monetized compute remain technical/service-scope questions; no blanket service entitlement or live verification is inferred.

## Decision and permission boundary

There is public support for third-party clients using **documented** Nuvio APIs subject to the service terms. There is insufficient evidence to approve every request made by the imported client, or Nuvio-backed identity for a separately monetized compute service. Public-client keys and GPL source permission do not independently authorize hosted service access.

The [public API reference](https://nuvio.tv/docs/nuvio-public-api.md), version 1.3, dated 2026-08-20, describes third-party client access, supported endpoints and internal/unsupported workflows. The [terms](https://nuvio.tv/terms), dated 2026-08-08, section 6 permits automation of APIs documented for public use while restricting overload, scraping and bypassing controls; section 9 separates source licensing from hosted services. This supports a conditional documented-client path, not an unrestricted service grant. We did not find explicit approval for the imported undocumented identity workflows or compute/billing integration in the sources inspected. That is an evidence gap, not a declaration that permission was denied.

| Proposed use | Evidence and decision | Release requirement |
| --- | --- | --- |
| Existing-account sign-in, refresh, current-user lookup and listed sync RPCs | Public reference documents these operations; terms apply | Confirm exact supported operations, consent, compliant traffic and fixture results; no blanket approval of the imported app |
| `get_sync_owner`, QR anonymous bootstrap/start/poll/exchange, device registration and other unlisted requests | Presence in Alpha source proves implementation intent only | Establish public documentation or explicit operator permission and semantics, or remove/disable the dependency in a separately reviewed change |
| Alternate auth hostname in Alpha configuration | Client source lists a fallback; inspected public API reference identifies the primary service | Verify operator control, credential destination permission and same identity trust domain before enabling fallback |
| Use of Nuvio identity for own-host pairing, entitlements, credits or paid processing | No explicit service-scope approval established in inspected material | Owner must record operator-authorized scope, capacity and security contract before release of these integrations |
| Source redistribution and branding | GPL source rights are separately audited; service/brand rights do not follow | Preserve [provenance](../UPSTREAM_SOURCES.md), [license gates](UPSTREAM_LICENSE_AUDIT.md), independent branding and corresponding source obligations |

The public API's rate section gives a per-user client safety guideline of at most **100 requests/second**, recommends RPC batching and reserves rate limiting. This is neither a throughput entitlement nor a suitable default polling target. No project-wide quota, SLA, verification budget or commercial capacity agreement was established. Future clients need much lower demand-driven traffic, bounded concurrency, pagination/deltas, deadlines, jitter/backoff and `429`/`Retry-After` handling. Do not evade limits through fallback hosts, accounts or IP rotation. This research sent no auth, sync or load-test requests.

### QR, host fallback and sync-owner caveats

[QrLoginService](https://github.com/alphasquare404/NuvioWeb/blob/5624da2fb26c19e4acad66a4f0cd4e4bcb8b74ff/js/core/auth/qrLoginService.js) may create an anonymous caller via POST `/auth/v1/signup` with `{data:{tv_client:"webos"}}`, falling back to `grant_type=anonymous`. It then calls `start_tv_login_session` with nonce/redirect/name, polls `poll_tv_login_session` with code/nonce, and exchanges at `/functions/v1/tv-logins-exchange`. It accepts snake_case, camelCase or nested session token pairs, stores them, clears the anonymous flag and directly sets authenticated state. The [QR screen](https://github.com/alphasquare404/NuvioWeb/blob/5624da2fb26c19e4acad66a4f0cd4e4bcb8b74ff/js/ui/screens/account/authQrSignInScreen.js) then routes to profiles; this exchange path does **not** itself call `establishAuthenticatedSession`. The separate similarly named AuthManager exchange method does establish the session and expects camelCase tokens. Neither path is a substitute for server verification. The QR renderer can send the login URL to an external QR image service when upstream supplies no image; assess login-code disclosure before enabling it.

[fetchSupabaseAuth](https://github.com/alphasquare404/NuvioWeb/blob/5624da2fb26c19e4acad66a4f0cd4e4bcb8b74ff/js/core/auth/supabaseAuthFetch.js) resends the same request to the configured alternate base on certain network errors, HTTP failures (including 408/5xx) or a response body indicating Cloudflare. This can forward **passwords, refresh tokens or bearer tokens**, including non-idempotent refresh/exchange requests. It does not retry `429` by status alone. A valid primary certificate or source example does not authorize the second credential recipient. Disable unapproved alternate destinations in any future release; no automatic redirect or destination derived from unverified token claims is allowed in a control-plane verifier.

[Profile sync](https://github.com/alphasquare404/NuvioWeb/blob/5624da2fb26c19e4acad66a4f0cd4e4bcb8b74ff/js/core/profile/profileSyncService.js) prefers `sync_pull_profiles`/`sync_push_profiles`, with table fallbacks keyed by effective owner and profile index. [Add-on sync](https://github.com/alphasquare404/NuvioWeb/blob/5624da2fb26c19e4acad66a4f0cd4e4bcb8b74ff/js/core/profile/librarySyncService.js) and [plugin sync](https://github.com/alphasquare404/NuvioWeb/blob/5624da2fb26c19e4acad66a4f0cd4e4bcb8b74ff/js/core/profile/pluginSyncService.js) also use that owner for table fallbacks. [Watch progress](https://github.com/alphasquare404/NuvioWeb/blob/5624da2fb26c19e4acad66a4f0cd4e4bcb8b74ff/js/core/profile/watchProgressSyncService.js) uses authenticated profile-scoped RPCs. This does not verify deployed RLS or the meaning of shared membership. `get_sync_owner` is absent from the inspected public reference; its client parser proves only a nonempty string expectation. Never assume it equals JWT `sub`, establishes household ownership, or grants spending authority. The official [self-host baseline SQL](https://github.com/NuvioMedia/self-host/blob/30f156807ae77b2aec80b091b0d513841a25ab91/database/migrations/00000000000000_baseline.sql#L585), lines 585–602, implements `get_sync_owner()` by rejecting null `auth.uid()` and returning that UID. This establishes equality for that published schema only; neither its deployment on the hosted service nor a hosted public API guarantee has been verified. Synthetic shared-owner cases below deliberately test that future authorization cannot collapse different subjects even if a deployment introduces delegation.

[Device registration](https://github.com/alphasquare404/NuvioWeb/blob/5624da2fb26c19e4acad66a4f0cd4e4bcb8b74ff/js/core/auth/deviceSessionRegistration.js) sends installation ID, client/version/platform/device name to `register_current_device` on authentication/foreground (15-minute interval except forced registration). This is an additional privacy/service-use boundary, not an account identity proof. Credential/profile sync can contain provider secrets; its existence grants no permission to export them to compute agents.

## Required future authoritative verification

This section is a design requirement for issues #7, #14 and #20, **not an implemented API**. The Nuvio reference documents GET `/auth/v1/user` with bearer access token and public-client `apikey`, returning `id`. [Supabase getUser guidance](https://supabase.com/docs/reference/javascript/auth-getuser) supports asking the auth server for an authentic user result. Availability and exact Nuvio behavior remain untested.

Conceptual internal result (never accepted from the browser):

```text
VerifiedIdentity {
  trustDomain: configured upstream authority,
  subject: authoritative user.id,
  sessionId: verified session reference if supported,
  expiresAt: validated access-token expiry,
  verifiedAt: control-plane timestamp,
  syncOwner: separately resolved namespace, optional,
  sessionStatus: active | unknown
}
Principal key = (trustDomain, subject)
```

1. Gate upstream use on approved service scope. Accept only an access token in the authorization header on a protected TLS control endpoint; never accept password/refresh token, URL token, browser-asserted user/owner/profile or an upstream URL. Limit token bytes, request size and rate; allowlist browser origins and apply CSRF protection if cookies are later introduced.
2. Select the configured upstream trust domain before parsing claims. Send GET `/auth/v1/user` only to a fixed approved origin/path, using the access token and public client key. No redirects, arbitrary hostname, fallback forwarding, admin/service-role key or response logging. Require a bounded JSON `200` with a valid nonempty stable `id`; other statuses, malformed bodies and timeouts deny verification. Invalid credentials map to unauthenticated; upstream failures map to unavailable without granting access or causing a billing/job side effect.
3. Confirm actual issuer, allowed audience, algorithm/key rotation, expiry and anonymous/session fields from operator documentation and later authorized fixtures. **These values are unknown here; do not copy an example issuer, assume the hostname is JWT `iss`, or use an anonymous client key as a signing secret.** Pin the allowed issuer/audience policy to the trust domain. Validate `exp`/`nbf` and bounded clock skew; cryptographically verified `sub` must equal the authoritative `id`. Deny anonymous/bootstrap, public-key-only and service-role credentials. If Nuvio exposes asymmetric signing keys, use a vetted library with a fixed approved JWKS URL and algorithm allowlist. For symmetric signing, rely on authoritative remote token validation; never obtain/distribute the signing secret. If the required claim or anonymous status cannot be established authoritatively, deny privileged use pending clarification.
4. Signature and user lookup alone do not promise immediate logout/revocation detection. [Supabase session guidance](https://supabase.com/docs/guides/auth/sessions) distinguishes token validity from live session existence. Require an operator-supported session-status check/attestation or documented equivalent for pairing, new paid reservations and entitlement mutations. Do not query privileged `auth.sessions` using acquired admin credentials. If upstream cannot provide this guarantee, record the limitation and keep those actions gated for human policy/security review; do not pretend `/user` proves current session liveness. Revoke NuvioWeb grants on its own logout/revoke events and bound their lifetime independently.
5. Derive the principal from the authoritative identity. Treat `syncOwner` as optional sync routing data fetched server-side with the **same token**, only when its API scope is authorized. It cannot replace subject or authorize household members to spend each other's credits, pair agents, export data or manage devices. A sync-owner change invalidates namespace caches; a subject/trust-domain/session change invalidates pending consent and grants even if owner/profile index is unchanged. Do not migrate balances or devices on email, profile name or shared-owner matches.
6. Check authorization and explicit consent per operation after identity verification; prevent duplicate/replayed operations atomically. Fail closed on uncertainty/outage. Privileged actions require fresh verification, no stale-owner/cache fallback. Minimize any later ordinary-read cache, bound it by token expiry and revocation policy, and never cache raw tokens persistently. Deadlines and request budgets must be agreed before launch; this document invents no upstream quota or price.

No Nuvio identities are issued by NuvioWeb. Internal agent/job credentials represent narrowly scoped permissions bound to the verified existing subject; they cannot log into Nuvio. Store only necessary identity bindings, device public identities, consent versions and entitlement/job records. Keep upstream tokens out of D1/queues/analytics/support reports, processing agents and build artifacts; access tokens exist transiently only where needed for verification. Refresh remains in the existing upstream browser flow pending a separately reviewed storage strategy. Treat localStorage XSS exposure and refresh races as open implementation risks.

## Consent and privacy boundaries

The [Nuvio privacy policy](https://nuvio.tv/privacy-policy) describes account/authentication and sync data, essential browser storage, diagnostics, and independent services' separate processing. It does not supply consent for this independent client's additional control plane. NuvioWeb must explain its own data recipients, purposes, retention and deletion controls before enabling those features.

| User action | Required scope and choice | Excluded implied authority |
| --- | --- | --- |
| Existing Nuvio login/sync | Explain credentials go to the approved Nuvio service, account data syncs there, browser stores session material; link upstream terms/privacy | No new password store, diagnostics upload, pairing, provider-secret export or charge |
| Optional control-plane feature | Explain access-token verification and minimal subject/device/operation records; allow local use if declined | No transfer of refresh tokens, passwords, full library/history or provider credentials |
| Pair own compute | Show exact device, subject, capabilities and revocation control; expiring one-time approval tied to current session | No Nuvio credentials on agent, no household-wide permission or platform processing fee |
| Hosted processing/payment | Separate quoted maximum charge, explicit authorization, reservation/hard caps and refund rules, verified subject and fresh session | Login, installed add-on, resolution/4K label or prior pairing never authorizes spending |
| Diagnostics/support | Explicit bounded disclosure, redaction and clear controls | No bearer/refresh tokens, passwords, cookies, login codes/nonces, API-key values or private media URL queries |

Consent records bind subject, purpose/version, selected agent/quote and time; recheck after account switch. Future control-plane sign-out must revoke this client's grants in addition to clearing local account state; remote logout/deletion semantics need separate authorized tests. Do not promise upstream account deletion also deletes third-party records or vice versa. Retention/deletion periods and any legally required payment records require review before collection; no new production data is collected here.

## Fallback when permission or verification is unavailable

The usable product fallback is the existing **continue without account** path with local profiles/settings/add-ons and compatible browser playback of user-authorized media. It uses no substitute Nuvio account/password database. Its source entry is `continueWithoutAccount` in the pinned [QR sign-in screen](https://github.com/alphasquare404/NuvioWeb/blob/5624da2fb26c19e4acad66a4f0cd4e4bcb8b74ff/js/ui/screens/account/authQrSignInScreen.js). This is an implementation path observed in source, not a newly verified browser release.

A future restricted release must bypass automatic QR/anonymous bootstrap and suppress **all** Nuvio-hosted traffic that lacks permission, including background sync, device registration and hosted avatars. Present account sync as unavailable, keep local data local and provide a return to the official client for existing cloud data. Metadata/add-on/media traffic still contacts selected third parties under their terms and browser/CORS limits; local mode is not a promise of zero network traffic. Do not deploy the current imported app claiming this restriction already exists.

If only undocumented APIs are unavailable, a separately reviewed change can retain permitted documented sign-in and RPC sync while eliminating unsupported owner/QR/table dependencies. No endpoint substitution or new login is implemented in this issue. Preserve local data; do not upload it automatically when permission returns, impersonate users with client IDs or silently map them to new accounts.

The official [self-host README](https://github.com/NuvioMedia/self-host/blob/30f156807ae77b2aec80b091b0d513841a25ab91/README.md) offers personal Docker hosting and discourages unofficial public backends. Its [client configuration](https://github.com/NuvioMedia/self-host/blob/30f156807ae77b2aec80b091b0d513841a25ab91/docs/client-configuration.md) documents discovery/build configuration. This is a possible future user-owned path, with user-paid infrastructure costs, not an implemented NuvioWeb fallback. Self-hosting an upstream backend does not automatically preserve existing Nuvio hosted identities or sync. Its separate issuer/subject namespace must never be silently linked by email or treated as hosted-account continuity. It is not an approved replacement identity system for this project. A future operator-supported user-owned deployment would need its own license/security/identity migration decision; changing the base URL or obtaining public source alone is insufficient. While extended service scope and authoritative live-session semantics are unresolved, shared agent pairing, entitlements and hosted payment launch remain gated; free compatible local playback remains the fallback target.

## Review gates, cost and rollback

Before releasing the imported hosted-account flow: human auth/privacy review; resolve unsupported API and alternate-host permission; verify subject/owner/anonymous/session semantics; test refresh/account isolation/QR disclosure; establish traffic budgets and publish accurate privacy disclosures. Before pairing or financial actions: separately resolve service-scope permission and live-session verification, then complete protocol/security/consent/cost gates. Unresolved permission is owned by the project owner and service operator; this task sends no outreach and asserts no approval.

No runtime files, licenses or imported history changed; no credential, payment or compute configuration changed; no media was relayed or processed. Documentation/public-source reads create no hosted compute spend. Future verification incurs upstream requests and control-plane costs that require bounded capacity planning. Neither free API documentation nor user-owned compute removes third-party service constraints. Plugin/SSRF/media isolation remains separately gated; credentials must never reach plugins, generic remote fetchers or media processors.

Rollback: revert this scoped documentation commit through review and restore matrix/decision/security references; retain evidence history. There is no runtime migration, account data mutation, deployment or bill to undo. The [feature matrix](FEATURE_SUPPORT.md) and [plan](plans/issues/issue-3.md) distinguish completed documentation checks from unexecuted contract/browser tests. ## QR publication and rendering disposition — 2026-10-20 (synthetic)

### Reachable sources and sinks

- `QrLoginService.start()` receives `qr_image_url`, `qr_content`/`web_url`, code and nonce from `start_tv_login_session`.
- The service previously fabricated `https://api.qrserver.com/v1/create-qr-code/...data=<login URL>` when upstream omitted an image. That recipient received credential-bearing QR content. The fallback is removed; the service now returns only the upstream image URL or `null`.
- The screen previously interpolated `qrImageUrl` into `innerHTML`. It now creates the image node with `document.createElement`, sets `src`/`alt` as properties and renders an explicit `data-state="unavailable"` message when the URL is absent or unsafe.
- `isSafeQrImageUrl` accepts only a same-origin HTTPS URL, the loopback HTTP origin used by tests, or a base64 `data:image/(png|jpeg|gif|webp)` URL. It rejects `javascript:`, cross-origin, credential-bearing, quote and control-character URLs.

### Attempt and publication boundary

- A QR attempt has an explicit id tied to the current `AuthManager` session generation. `start`, `poll` and `exchange` check ownership after every await; a superseded/cancelled exchange cannot write tokens, authenticate an anonymous session or navigate. The screen's post-await check is no longer the only protection.
- Successful exchange publishes through `AuthManager.establishAuthenticatedSession()` with a new authentication attempt. Sign-in, TV exchange, bootstrap and sign-out advance the authentication-attempt sequence so a stale completion cannot overwrite a later session.
- Cleanup invalidates the attempt and clears an unapproved anonymous caller's tokens. Already-issued remote requests cannot be undone; only local publication is controlled.
- QR error text is redacted for the code and nonce; console diagnostics use fixed messages.

### Consent, recipients and residual risk

- No new credential recipient, endpoint, dependency or authentication service is introduced. The QR flow still sends its documented requests only to the configured configured upstream identity origin; the third-party renderer is gone.
- QR approval/consent/expiry/nonce/device semantics are not verified here. A successful synthetic poll/exchange is not live QR support.
- Access/refresh tokens remain same-origin `localStorage` values; a same-origin script/XSS can still read them. This change does not replace the storage model, eliminate XSS, or prove server-side revocation. Local cleanup is not remote logout.
- Review disposition: targeted lifecycle/browser tests and a separate automated review (recorded, not independent human approval) cover the publication and rendering invariants. Live QR remains an owner/service gate.
