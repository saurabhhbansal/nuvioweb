# Issue #10 — Chromium HEVC feasibility, 2026-10-20

## Verdict and boundary

**Chromium can play HEVC; this is not an engine-wide impossibility. This tested Linux ARM64 build/host rejects these HEVC inputs. Application JavaScript and installing system FFmpeg cannot manufacture an absent native decoder path.** Upstream separates proprietary-codec configuration, parsing/demuxing and platform decoding. Its published codec table describes HEVC as requiring hardware support. [Chromium codec documentation](https://www.chromium.org/audio-video/#codec-and-container-support) · [exact156 build gates](https://github.com/chromium/chromium/blob/156.0.8078.4/media/media_options.gni#L124-L173) · [exact156 runtime profile gate](https://github.com/chromium/chromium/blob/156.0.8078.4/media/base/supported_types.cc#L231-L250).

## Build flags are different gates

The following uses upstream **tag156.0.8078.4**, matching the reported installed version, not an assumption about that binary's compiled GN arguments:

- `proprietary_codecs` gates proprietary codec/demuxer support and advertised types. Its156 default includes `is_chrome_branded` **and `is_chrome_for_testing_branded`**, plus Cast. It is not a bundled software-HEVC decoder. [156 features](https://github.com/chromium/chromium/blob/156.0.8078.4/build/config/features.gni#L17-L31) · [advertisement distinction](https://www.chromium.org/audio-video/#proprietary_codecs).
- `ffmpeg_branding = "Chrome"` selects Chrome's FFmpeg codec configuration rather than Chromium's subset. The FFmpeg revision pinned by156 is `9db86ce5b5b454dfc96c435f9f0723012980c37f`; its options also default Chrome-for-Testing branding to `"Chrome"`. **This is not equivalent to enabling HEVC decoding.** The Chrome/Linux/ARM64 configuration enables AAC/H.264 decoders, and Chromium's `FFmpegVideoDecoder::IsCodecSupported()` explicitly accepts **only H.264**. Installing command-line FFmpeg cannot change that selection code. [156 dependency pin](https://github.com/chromium/chromium/blob/156.0.8078.4/DEPS#L540) · [pinned FFmpeg options](https://chromium.googlesource.com/chromium/third_party/ffmpeg/+/9db86ce5b5b454dfc96c435f9f0723012980c37f/ffmpeg_options.gni) · [Chrome ARM64 FFmpeg configuration](https://chromium.googlesource.com/chromium/third_party/ffmpeg/+/9db86ce5b5b454dfc96c435f9f0723012980c37f/chromium/config/Chrome/linux/arm64/config.h) · [156 video-decoder restriction](https://github.com/chromium/chromium/blob/156.0.8078.4/media/filters/ffmpeg_video_decoder.cc#L70-L140).
- `enable_hevc_parser_and_hw_decoder` includes HEVC parsing/hardware-assisted integration. The156 expression requires `proprietary_codecs` and allows Linux, Windows, Apple, Android or fuzzing. The nearby comment omits Linux, but the executable GN expression includes it. `enable_platform_hevc` enables **demuxing**, explicitly requiring platform-provided decoding; its default depends on the parser/hardware gate or Cast. These are build-time GN values, not JavaScript options or arbitrary launch flags. [156 definitions/assertions](https://github.com/chromium/chromium/blob/156.0.8078.4/media/media_options.gni#L124-L198).
- Linux is an optional-HEVC-decode platform. `IsDecoderHevcProfileSupported()` checks compiled HEVC support and the supplemental decoder-profile cache: a parser-enabled binary can advertise no HEVC when no platform profiles exist. `PlatformHEVCDecoderSupport` already defaults enabled in156 when compiled; adding that feature name cannot supply an absent decoder/device. [156 profile gate](https://github.com/chromium/chromium/blob/156.0.8078.4/media/base/supported_types.cc#L231-L250) · [156 runtime feature](https://github.com/chromium/chromium/blob/156.0.8078.4/media/base/media_switches.cc#L1210-L1226).

**Current upstream versus installed156:** fetched `main` has the same HEVC GN expressions and an identical supported-types implementation. The inspected options-file difference changes experimental **Symphonia demuxer** defaults, not HEVC decoding. Main has other media-switch changes, including timed HDR-metadata handling; none proves installed156 playback. No main binary was built/run. [Current options](https://github.com/chromium/chromium/blob/main/media/media_options.gni) · [current supported types](https://github.com/chromium/chromium/blob/main/media/base/supported_types.cc) · [current switches](https://github.com/chromium/chromium/blob/main/media/base/media_switches.cc).

## HEVC SDR decoding is not HDR output

The SDR Main row already fails, so an unavailable HDR screen alone cannot explain **all three** Chromium failures. Main10/PQ/HLG additionally require bit-depth/profile and color handling. Decoding tagged pixels, interpreting metadata/tone mapping and physically outputting HDR luminance/gamut are separate claims. MediaCapabilities reports configuration support and **expected** smoothness/power efficiency; HDR fields describe interpretation/mapping, not measured screen output. [SDR evidence](../evidence/issue10-engine-2026-10-20.json#L171-L223) · [MediaCapabilities configuration](https://www.w3.org/TR/media-capabilities/#videoconfiguration).

Chromium156's supported-types check accepts static ST2086 metadata only with PQ and rejects the listed ST2094 dynamic-metadata types; this is not universal HDR10+/Dolby Vision certification. **Port-specific example:** current WebKit GStreamer code under `ENABLE(WPE_PLATFORM)` rejects explicit HDR-metadata/PQ/HLG capability configurations without HDR screen data. Such a capability negative can coexist with successful HDR-tagged byte decoding. This is conditional/current-upstream source, not installed WPE27.2 compile-option proof or a claim Apple's port behaves identically. [Chromium metadata gate](https://github.com/chromium/chromium/blob/156.0.8078.4/media/base/supported_types.cc#L71-L93) · [WPE/GStreamer source](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/graphics/gstreamer/GStreamerRegistryScanner.cpp) · [output boundary](../ENGINE_CAPABILITY_MATRIX.md#L60-L68).

## Licensing, security and cost

Code licenses, HEVC patents, vendor-binary terms and media rights are distinct. FFmpeg documents LGPL/GPL obligations and jurisdiction/commercial-use patent uncertainty. HEVC has active patent-pool licensing with product/territory/rate distinctions; this note determines neither applicable royalties nor coverage. Do not redistribute a codec/browser or claim worldwide commercial royalty freedom because a private FFmpeg toolchain decodes HEVC. Conversely, these sources do **not** establish an obligatory paid codec purchase or processing service for every user. Preserve source/notices obligations and obtain distribution/jurisdiction-specific advice before shipping a custom codec build. [FFmpeg legal guidance](https://ffmpeg.org/legal.html) · [HEVC pool terms/rates](https://accessadvance.com/hevc-advance-patent-pool-detailed-royalty-rates/) · [Playwright licensing distinction](https://playwright.dev/docs/browsers#media-codecs).

Do not follow troubleshooting examples that disable driver safeguards, sandboxing, web security or protected-media policy to produce a pass. Do not buy extensions, rent GPUs, upload media or introduce transcoding/relays for this research. The useful next evidence is **one known-capable native decoder plus the unchanged SDR fixture**, followed conditionally by Main10 and separate physical HDR validation—not another brand matrix or a lowered quality criterion.
