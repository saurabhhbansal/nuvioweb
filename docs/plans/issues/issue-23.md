## 2. Proposed automation

### Scope and non-goals

Implement complete monitoring for the approved Alpha `web` baseline first. Record every other documented reference in the manifest, with its existing pin or an explicit missing-pin status.

Only Alpha monitoring is initially enabled. Enabling another source requires a reviewed manifest change naming its branch, checkpoint, licensing evidence and request budget. Missing native pins must not be filled by automatically trusting a moving default branch.

This ticket does not authorize:

- Fetching/importing upstream Git history into project branches.
- Updating application source, dependencies, import pins or tags.
- Opening port PRs, merging changes, deploying services or changing feature-support claims.
- Downloading release assets, executing upstream code or running upstream workflows.

### Collector

Add a dependency-free Node script using built-in `fetch`, crypto, filesystem and test APIs.

Proposed interface:

```sh
node scripts/upstream-watch.mjs \
  --state docs/upstream/state.json \
  --report dist/upstream-watch/report.json
```

The collector performs GET requests only:

1. Validate the protected manifest and parity records.
2. Resolve the configured Alpha branch once to an immutable candidate SHA.
3. Compare both:
   - Original import pin → candidate: total upstream drift.
   - Reviewed checkpoint → candidate: outstanding review work.
4. Obtain bounded commit comparisons and complete recursive Git-tree inventories where available.
5. Compare blob IDs, paths and modes to identify changed files, including additions and deletions.
6. Compare tag-name/target-SHA inventories and release metadata against the last human-approved observation baseline.
7. Check license/notice inventory changes.
8. Re-read the branch ref; report an unstable scan if it changed during collection.
9. Emit a bounded, validated JSON report.

Use fixed GitHub REST endpoints for branch refs, commit comparisons, commit/tree metadata, tags and releases. Pin the API-version header. Pagination and response handling must be exercised with fixtures and confirmed during the later controlled workflow smoke; no live API behavior is claimed by this plan.

Comparisons must distinguish identical, ahead, behind and diverged histories. Missing checkpoints, unavailable objects, incomplete pagination and truncated trees produce explicit incomplete results.

### License and notice monitoring

Maintain an approved inventory containing:

- Root LICENSE and its audited digest.
- License/notice/copyright files discovered by path.
- Audit-specific files, including the QR library, attribution screen, README and relevant asset notices.
- Package manifests, lockfiles, font/binary assets and packaging scripts as licensing-review triggers.

Compare inventories across complete trees. Added, removed, renamed or changed relevant files become findings. Preserve both old and new paths/blob IDs; a rename must not hide a removal.

Report licensing states such as:

- `tracked-notices-unchanged`
- `drift-detected`
- `missing-required-license`
- `unknown`

Changed dependency declarations, assets and bundled code require review even if the root GPL text is unchanged. This check detects inventory drift; it cannot certify file-header attribution, component rights or complete release compliance.

Do not install dependencies or download package tarballs for monitoring.

### Change classification

Produce conservative suggestions using changed paths and known subsystems:

- Critical-bugfix candidate.
- Compatible-feature candidate.
- Incompatible-change candidate.
- Native-only candidate.
- Browser-no-op candidate.
- Unclassified.

Every suggestion carries its basis and `reviewRequired: true`. Default to unclassified. Commit titles, release names and path heuristics cannot establish compatibility or device support.

### Scheduled workflow and single tracker

Add `.github/workflows/upstream-watch.yml`:

- Weekly schedule: `23 6 * * 1`, UTC.
- Manual `workflow_dispatch`, with no arbitrary repository/ref inputs.
- Execution restricted to this repository’s `main`.
- Workflow-wide concurrency group; `cancel-in-progress: false`.
- Separate collection and publication jobs.

Publication maintains **one persistent tracking issue and one bot-owned report comment**:

- Exact issue marker: `<!-- nuvioweb-upstream-watch:v1 -->`
- Exact report-comment marker: `<!-- nuvioweb-upstream-watch-report:v1 -->`
- Fixed issue purpose and title.
- Human discussion remains in separate comments.
- Update the existing report comment only when its semantic fingerprint changes.
- No per-commit issues, repeated comments, assignments, labels or automatic closures.

Prefer explicit issue/comment IDs once recorded through a reviewed state-file update. Initial discovery must inspect bounded, fully paginated results and verify markers, repository and bot ownership. If discovery is incomplete or ambiguous, refuse creation.

The persistent tracker remains open after implementation issue #23 closes. The existing completion guard reopens unsupported closures of untracked issues; document that interaction without weakening the guard or inventing completion evidence for the tracker.

## 3. Data and contract design

### Protected state

Use `docs/upstream/state.json` as the machine-readable, PR-reviewed checkpoint. Do not create a second feature-support matrix.

| Field | Contract |
| --- | --- |
| `schemaVersion` | Integer `1`; reject unsupported versions |
| `sources[]` | Stable ID, canonical repository, explicit ref, enabled state and reuse boundary |
| `import` | Immutable original SHA/tree, destination, import commit/tag and provenance evidence |
| `reviewedThroughSha` | Human-approved review checkpoint; independent of the import pin |
| `licenseBaseline` | Audited SHA, required paths, blob IDs/digests and audit reference |
| `observationBaseline` | Approved tag-name/target-SHA map and release metadata; initially absent |
| `decisions[]` | Reviewed commit/range, disposition, rationale and discussion/evidence links |
| `ports[]` | Upstream SHA/path → local path/PR/commit, attribution, tests and remaining limits |
| `tracking` | Target repository and optional established issue/comment IDs |
| `limits` | Validated bounds; cannot exceed implementation hard ceilings |

Bootstrap `reviewedThroughSha` to the original Alpha baseline with the explicit meaning “audited/imported starting point.” It must not imply full browser parity.

For an initial tag/release scan, report `baseline-review-required`; do not present every existing tag as newly published. A human reviews the inventory before recording its baseline.

### Report

Document the versioned report in `docs/upstream/report.schema.json`; implement validation without adding a schema-library dependency.

| Field | Meaning |
| --- | --- |
| `schemaVersion` | Report version |
| `projectSha`, `stateSha256` | Exact project revision and input-state identity |
| `generatedAt` | Observation timestamp; excluded from semantic fingerprint |
| `status` | `complete`, `partial` or `error` |
| `sources[]` | Configured source and observation result |
| `sources[].refs` | Import, reviewed and observed immutable SHAs |
| `sources[].comparisons` | Relationship, counts, bounded commit IDs and completeness |
| `sources[].files` | Changed-path totals, bounded details and sampling flags |
| `sources[].tags` | Added, removed and retargeted names/commit targets |
| `sources[].releases` | Release IDs, tag names and publication-state changes |
| `sources[].license` | Inventory findings, evidence identifiers and review state |
| `sources[].parity` | Matching recorded decisions/ports and unresolved review work |
| `findings[]` | Stable ID, kind, severity, evidence and review requirement |
| `errors[]` | Fixed error code, affected operation and retryability |
| `limits` | Requests/bytes consumed, caps reached and truncation indicators |
| `fingerprint` | SHA-256 of canonical semantic content |

Use stable ordering and deduplicate by source plus immutable object identities. Separate complete collection from sampled display details. If a required inventory is incomplete, the overall report cannot say “no changes.”

GitHub’s tags listing provides commit targets. Annotation-only changes to annotated tags are outside the initial contract and must be stated as a limit.

### Bounds and failure behavior

Initial hard ceilings:

| Resource | Ceiling |
| --- | --- |
| Enabled sources | Alpha `web` only |
| Collector requests | 40, including retries |
| Publisher requests | 12 |
| Commit details | 200 across at most two pages per comparison |
| Tag/release inventories | 100 entries each; detect overflow |
| Recursive tree | 5,000 entries; reject API truncation |
| Individual API response | 2 MiB, enforced while reading |
| Collector wall-clock deadline | 180 seconds |
| Individual request deadline | 10 seconds |
| JSON report | 48 KiB |
| Published report comment | 60 KiB |

If a bound prevents complete analysis, emit a compact incomplete report identifying the bound. Never silently discard required findings to fit the report.

Exit behavior:

- `0`: complete observation, including observations containing changes or license alerts.
- `1`: invalid configuration or local contract failure.
- `2`: partial/unavailable remote observation.

A failed observation never advances approved state. An established tracker may receive one changed health report, preserving the previous successful observation as historical evidence. Repeated identical failures cause no repeated writes. Missing or invalid collector output prevents publication.

For rate limits, inspect response status and rate-limit headers. Permit at most one bounded retry for idempotent GET requests when the remaining deadline and request budget allow it. Do not wait through a long reset interval.

### Idempotency and issue-write recovery

Fingerprint changes include upstream identities, parity-state changes, licensing findings and health transitions. Exclude timestamps, request IDs and remaining-rate counters.

Publication must:

1. Revalidate the report against the checked-out project SHA and state digest.
2. Find the established issue/comment.
3. Compare the stored fingerprint.
4. Perform no write for an identical report.
5. Edit only the bot-owned report comment.

Do not blindly retry an ambiguous issue/comment creation after a timeout. Reconcile by marker on the next attempt; if reconciliation is inconclusive, stop. Serialize scheduled and manual runs to prevent competing creators.

A closed or ownership-mismatched tracker is an operator-visible error, not permission to create a replacement.

### Permissions and report transport

- Workflow default: `contents: read`.
- Collector: read-only token permissions; GET access to explicitly configured public GitHub sources.
- Publisher: `contents: read` and `issues: write`, scoped to the target repository.
- No PAT, application credentials, Nuvio tokens or external secrets.
- No contents-write, pull-request-write, packages-write or deployment permission.

Pass the bounded JSON between jobs as base64 in a job output, using a fixed environment variable in the publisher. Validate decoded size and schema before rendering. Never interpolate it into shell source.

Keep the local JSON report under ignored `dist/`. Include its machine-readable JSON in the bounded bot report comment so it remains inspectable without adding artifact actions or dependencies.

### Human approval of parity updates

Monitoring never edits protected state.

A maintainer reviews a finding and submits a PR that records one of: ported, deferred, rejected, native-only or browser-no-op. Advancing a reviewed checkpoint requires explicit coverage of the reviewed range; it does not change the original import pin.

A port record requires source SHA/path, destination, attribution/licensing evidence, merged port PR and exact verification evidence. Unsupported or untested capabilities stay marked accordingly in `docs/FEATURE_SUPPORT.md`.

Local validation checks structure and evidence references. Human review and protected PR integration establish approval; the validator must not claim to prove remote merges or test truth.

## 4. Security, privacy and cost

- Fetch only allowlisted `https://api.github.com` endpoints for configured repositories. Reject redirects and arbitrary URL/ref overrides.
- Treat response strings, paths, tag names and release metadata as untrusted data.
- Do not execute upstream code, evaluate configuration, invoke package hooks, download binaries, extract archives or check out upstream trees.
- Do not copy upstream commit bodies or release prose into shell commands, workflow commands or issue instructions.
- Escape Markdown, HTML, mentions and workflow-command syntax. Publish metadata and identifiers, not raw code patches or API error bodies.
- Reject traversal, symlink-following and unsafe report-output paths.
- Do not log authorization headers or credentials. Reports contain no account, playback or private media data.
- Reuse existing immutable action pins:
  - Checkout: `11bd71901bbe5b1630ceea73d27597364c9af683`
  - Setup Node: `49933ea5288caeca8642d1e84afbd3f7d6820020`
- Use `.node-version` and `persist-credentials: false`.
- No dependency installation or application build in scheduled monitoring.
- Collector timeout: four minutes; publisher timeout: two minutes. Weekly execution bounds this workflow to roughly 30 scheduled runner-minutes per month, excluding manual runs and existing PR checks.
- No auto-import, auto-merge, deployment, payment or hosted-compute behavior.

The new issue-writing path needs owner review of the concrete permission boundary before publication is enabled, as required for new privileges. Read-only monitoring and publisher dry-run verification can be completed first.

## 6. Risks, limits and manual responsibilities

| Risk or limit | Required handling |
| --- | --- |
| GitHub API changes or unexpected response shapes | Strict validation and versioned contracts; report unknown/error rather than inventing an empty result |
| Rate limits and transient outages | Bounded GET retries; visible incomplete status; no checkpoint advancement |
| Compare/tree/report limits | Explicit completeness flags; require a separately planned investigation when bounds are exceeded |
| Force-pushed branches, missing commits or deleted repositories | Raise history-integrity findings; never reset approved pins automatically |
| Tags/releases changing during pagination | Best-effort observation only; detect inconsistencies where possible and retry on a later run |
| Annotation-only tag edits | Initial monitoring tracks tag commit targets; annotation changes remain manual |
| False compatibility classifications | Suggestions only; reviewers determine the final disposition |
| Hidden security fixes or inline notice changes | No semantic/security/legal completeness claim; review source diffs before ports |
| GPL/AGPL, fonts, WASM, binaries and dependency drift | Block reuse decisions pending component review; monitoring cannot grant redistribution rights |
| Divergence caused by local Alpha patches | Preserve original pin separately from reviewed checkpoints and port records |
| Workflow delays or disabled Actions | Weekly scheduling is best effort; manual invocation and documented local operation remain available |
| Tracker races or ambiguous creation failures | Serialize runs, reconcile by exact markers, refuse uncertain replacement creation |
| Human parity approval | Required through reviewed state-file PRs; tracker checkboxes and bot reports do not approve updates |
| Browser/device/service parity | Remains governed by the existing evidence matrices and relevant issues |
| Reference forks and native sources | Recorded explicitly but initially unmonitored; enabling them requires reviewed pins and budget allocation |

Issue #23 is complete when fixture-backed monitoring, protected offline checks, reviewed tracker publication, an observed idempotent run, and the documented human parity process are evidenced. It does not require importing the detected changes or resolving unrelated device and live-service gaps.
